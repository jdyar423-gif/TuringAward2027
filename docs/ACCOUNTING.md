# 參數計帳規則

「總參數 ≤100M、每 token 活躍 ≤20M」的宣稱只有在定義釘死之後才有意義。這裡寫下採用的定義、另一種更嚴格的讀法，以及稽核方式。

## 定義

- **一個參數**＝一個隨模型出貨、至多 16 位元的數字。
- **總量**＝出貨的全部數字：稠密權重、查表、暫存器與候選的嵌入表、藏書（壓縮後位元組數 ÷ 2）、檢索索引與文件頻率表。分詞器的合併表與由它決定性導出的轉移表不計（慣例上分詞器不算模型參數）；除此之外，沒有任何「載入時衍生」的資料結構被排除在外。
- **活躍（標準口徑）**＝在已有快取狀態下，產生一個 token 的完整機率分佈時讀到的相異數字。稠密與迴圈權重全算（重複使用只算一次）；查表只算被讀到的列；輸出頭全算；藏書只在檢索那一步讀取索引項與一到兩個壓縮區塊。這是 MoE 模型名稱中「A」的慣例（每個位置一次前向）。
- **活躍（嚴格口徑）**＝輸出在函數上相依的所有數字，包含整個語境視窗內各位置讀過的表列。這個讀法下，token 索引表的成本乘上視窗內相異 token 數。

| 迴圈核心 | 14,118,912 | 全部 |

| 正規化、通道、匯點、信任頭、評分頭等 | ≈0.31M | 全部 |

### 兩種口徑的實測

以真實文本（6 份 ClimbMix 文件、真實精確層）用讀取集稽核量到的數字，不含評分頭（+0.197M，啟用時才讀）與藏書讀取（只在檢索那一步：分析上界 +0.245M）：

| 配置、視窗 | 標準口徑（每步，最大） | 嚴格口徑（最後一個位置） | 視窗內相異 token |
|---|---|---|---|
| `final`，T=1024 | 18.83M | 19.62–19.81M | 376–482 |
| `final`，T=2048 | 18.83M | 20.07–20.49M | 606–837 |

所以預設配置滿足標準口徑（加上評分頭與檢索最壞情況為 19.28M）。嚴格口徑在 T=1024 且不檢索時滿足；若把評分頭與檢索那一步的讀取也算進去，T=1024 約 19.8–20.2M、T=2048 超出 0.3–0.9M。計畫核准時採標準口徑為預設、嚴格口徑並列報告。若要兩種口徑都低於 20M，使用 `configs/strict.py`（前饋層寬度 3072→2688、評分頭 256→128，稠密核心少約 6%）：含藏書檢索的最壞讀取量在內，`bes/budget.py` 的視窗上界公式在 T=2048、840 個相異 token 時為 19.85M（同一公式對 `final` 給 21.13M；實測的函數相依讀取集比這個公式低 0.4–0.8M）。

### `configs/v9.py`（無藏書，逐詞頁）

帳本見 `docs/V9.md` 第 5 節：總量 98,036,104，每步讀取 19,631,240（標準口徑，含評分頭）。逐詞頁讓嚴格口徑下視窗內每個相異 token 多讀 9,536 個數字（輸入嵌入、逐圈 value embedding、輸出增益、私有神經元的鍵與值、候選輸入表），所以 v9 只滿足標準口徑。以 40 份 ClimbMix 樣本文件（各至少 2,048 個 token，真實精確層，不含評分頭）用讀取集稽核量到：

| 配置、視窗 | 標準口徑（每步，最大） | 嚴格口徑（最後一個位置：最小／中位數／最大） | `bes/budget.py` 視窗上界（中位數／最大） |
|---|---|---|---|
| `v9`，T=1024 | 19.43M | 21.2M／23.8M／24.6M | 24.2M／25.0M |
| `v9`，T=2048 | 19.43M | 22.4M／26.7M／28.2M | 27.1M／28.6M |

## 稽核

`bes/readset.py` 提供一個只吃「被讀到的列」的 NumPy 參考前向：
1. 與 JAX 模型的對數機率差 ≤1e-4；
2. 對所有未被讀到的表列加入大幅雜訊，輸出不變；
3. 記錄每個生成 token 讀到的相異數字數（兩種口徑）。

訓練時為了硬體效率會對整張表做稠密運算再遮罩；這不改變函數，也不改變上述計數。

## 推論時計算

粒子解碼對同一個模型取樣 K 次。每個粒子的每一步讀到的數字相同，所以活躍數不變；計算量乘以 K。評測報告會同時列出 K=1 的結果，並讓對手也以同樣的 K、用自身對數機率選最佳作為對照。
