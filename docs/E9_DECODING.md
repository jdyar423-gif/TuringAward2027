# E9 — particle decoding, stand-in measurement on CPU

Generated by `scripts/e9_standin.py run` then `scripts/e9_standin.py report` (the table between the markers is written by the script; the report scores the saved replies again with the current `bes/eval/exact_score.py`, and counts a reply that used its whole token budget as cut, see "Finishing"). Every number is measured on this machine; nothing is extrapolated.

**What this is.** Our decoder (`bes/decode`: potentials, particle filter, satisficing selection, through `bes/decode/respond.py`) drives an *opponent* chat model, `Falcon-H1-Tiny-90M-Instruct-Q8_0.gguf`, through `bes/decode/gguf_lm.py` (llama-cpp-python 0.3.37, low-level calls). Our own model has no trained checkpoint yet, so the gate cannot be measured on it; this stand-in measures what the decoding machinery does to a real small chat model. Section "What this can and cannot tell" says how far that carries.

## Setup

- **Prompts**: the dev half of `bes/eval/proxy/prompts.jsonl` only (the held-out half is never decoded): all 47 dev prompts that carry a machine-checkable constraint (35 single-turn, 12 two-turn) and a fixed sample of 16 single-turn dev prompts without one (4 chat, 4 writing, 3 code, 5 math; the first in the split's hash order). 63 prompts; 63 turns decoded by every arm (the 12 unconstrained first turns are decoded by the plain arm and shared, see below).
- **In-sample for the constraint compiler.** These 47 constrained prompts were also the development set of the constraint compiler (`bes.exact.constraints.compile`): it was extended until it matched the annotations on 42 of them (`docs/CHANGES.md` section 7) and the tests pin its output on these turns. The filter and the potentials can only act on what the compiler reads, so the gains below are measured where the compiler is at its best: it reads every annotated constraint of 45 of the 47 (96%; the two misses are the deliberate ones, an approximate "about 100 words" and unquoted details). On the held-out half, counted in aggregate only (no held-out prompt or miss is printed, and the compiler was not changed after looking), it reads every annotated constraint of 41 of the 48 constrained prompts (85%; 49 of 56 constraints). On unseen prompts more explicit requests go unread, neither enforced nor filtered, so expect smaller gains than here (the report's last line recomputes both counts).
- **Arms** (same `Responder`, same model, same seeds; the model's recommended llama.cpp settings, the ones the harness uses for this opponent: temperature 0.8, top-k 40, top-p 0.95, min-p 0.05, no repetition penalty; no n-gram blocking and no copy cap in any arm, so the arms differ only in what the gate asks about):
  - `plain`: one particle, no potentials: ordinary sampling, draw for draw;
  - `filter`: six particles, no potentials; failure filter, length band and lexical consensus (`bes/decode/select.py`);
  - `potentials`: six particles with the exact potentials of the compiled constraints (structure, counts, reachability pruning, budget aware), resampling at sentence boundaries when ESS < K/2, and the same selection.
- **Budget**: 320 new tokens per particle (`max_new_tokens`); the prompt is rendered with the model's own chat template; `END` is its `<|im_end|>` and the probability of every end-of-generation token is moved onto it (what llama.cpp's own loop does).
- **Paired design**: every turn is seeded with the same `derive_seed(seed, prompt id, turn)` in every arm, and the random draws of a particle depend only on its slot and token position, so without potentials the first particle of a six-particle arm *is* the plain arm's sample. In a two-turn prompt whose first turn has no constraint, every arm continues the plain arm's first reply, so the arms decode the same constrained turn after the same conversation; length, finishing, degeneracy, fluency and cost below count the 63 turns every arm decoded itself.
- **Code version**: the run used the constraint compiler as it was on disk at 18:12 UTC; it was rewritten during the run (more instruction families), and the new version compiles exactly the same specification for all 63 decoded turns.
- **Scoring**: `bes/eval/exact_score.py` (the harness's own constraint checks, degenerate detectors and math answer extraction), Wilson 95% intervals (`bes/eval/proxy/score.py`), exact sign tests on the paired prompts.
- **Machine**: 2 worker processes, 1 llama.cpp thread and 1 numpy thread each, on the 4-core container while other work kept the load average at 7-9 (each worker got about half a core). Wall time 1504 s for the run (plus 77 s for two pilots of 2-3 prompts); peak memory about 450 MB per worker. Records: `data_cache/e9_standin/records.w*.jsonl` (resumable), summary `data_cache/e9_standin/summary.json`.

## Reading the numbers

- **Constraints.** Plain sampling satisfies every constraint of 66% of the constrained prompts [52, 78]; six particles with the failure filter and consensus 91% [80, 97]; with the potentials as well 98% [89, 100]. Paired on the same prompts: filter better than plain on 12 prompts and worse on none (sign test p = 0.0005); potentials better than plain on 15, worse on none (p = 0.0001); potentials better than filter on 3, worse on none (p = 0.25, not resolved). Most of the gain is already the filter's: six samples of this model usually contain one compliant reply for keywords, case, one-of answers, word frequencies and list markers. The potentials add what all six samples miss: exact sentence counts (4/6 -> 6/6), the paragraph count (0/1 -> 1/1). The one prompt the potentials arm still fails (instruct-068, "do not use the word "leaves"") asks for a forbidden word, which the potentials do not enforce; none of its six particles avoided the word.
- **Finishing.** 17% of plain replies and 11% of filtered ones are cut at the 320-token limit. With the potentials no particle is cut by the limit itself (378 of 378 finished), because the budget-aware masks keep every particle able to finish; but 9 of the 63 replies of the potentials arm (14%) end exactly at the budget: the masks left only `END` in the last slot, so these replies are cut by the budget in all but name (they stop inside a list, after a heading, or mid-sentence). The table counts them as cut and as degenerate, as `bes.decode.respond` now reports them (finish reason `length`, `extra["at_budget"]`; when this run was made it said `stop`, and an earlier version of this table showed 0/63 here). So the potentials do not avoid running out of budget, they turn "cut at the limit" into "ended at the budget": 9 cut replies against 7 with the filter and 11 with plain sampling. In 8 of the 9 all six particles reached the budget, i.e. the model was writing a longer answer than the budget on those prompts (open questions, lists, code). The text detector `select.cut_off` catches only one of them (most end in a heading, a list line or a short fragment).
- **Degenerate output** other than running out of budget: none in any arm (0/63).
- **Length** barely moves: mean 70-76 words, median 58-64 in all arms; the length band rejected a few long open answers (rule `relax_band` 5-6 times: no particle in the band).
- **Fluency proxy.** Mean log-probability per token under the model: -0.467 (plain), -0.464 (filter), -0.492 (potentials). Paired on the same turn the filter changes it by +0.004 ± 0.015 and the potentials by -0.025 ± 0.019 nats per token (1.3 standard errors: not significant). The pooled value drops more (-0.379 -> -0.447) because it weights long replies, where the forced endings are.
- **Rejected particles.** 45% of the filter arm's particles and 25% of the potentials arm's fail at least one check (unfinished, violation, degenerate, outside the band).
- **Cost.** Six particles produce 5.6x (filter) and 5.8x (potentials) the response tokens of plain sampling, in 1.3x and 1.8x the decoder steps (one batched model call per step; sentence-boundary waiting adds steps) and 3.4x and 4.0x the CPU seconds per turn on one thread. 14 of 63 turns resampled in the potentials arm (18 events), 3 in the filter arm (when four or more particles reach the budget their weight is 0).
- **Math** (5 prompts: 3/5, 4/5, 3/5) resolves nothing, but shows two mechanisms. In math-051 the budget-aware potentials let six long, wrong derivations finish and the majority vote took their common wrong answer (-88), while in the filter arm three particles were cut at the budget and the three that finished included the right one (56). In math-013 the potentials arm's reply ends "Therefore, \( 7! = 5040 \)."; when this run was scored, `exact_score.extract_answer` split that sentence at "7!" and read 7 (the earlier version of this table had 2/5), and the selector's vote, which uses the scorer's rule, shared the misreading during the run. The scorer no longer ends a sentence after a factorial, so the reply is now scored right.
- **Selection in this run.** The selections were made before two changes found by reading these records: `cut_off` treated a line starting with bold markup (`**Energy**: ...`) as a list item and so never fired on it, and there was no `at_budget` check. The `cut_off` and budget rows of the table are recomputed on the saved replies with the corrected detector. The selector now drops a finished particle that used its whole budget (`at_budget`) when another one ended on its own; in 8 of the 9 affected turns there was none, so the outcome could only change for one turn (instruct-019).

## What this can and cannot tell about our own model

What it shows:

- The machinery works end to end on a real chat model and a foreign vocabulary: constraint compilation from the user's words, exact potentials with reachability pruning, budget-aware finishing, resampling with state copies, the failure filter, the length band and the consensus, all through the same `Responder` the harness will call for our model.
- For the count and format constraints the potentials enforce (words, sentences, items, lines, paragraphs, no commas, end with a question, code block), a finished particle satisfies them by construction as our verifier counts them (the harness's checker has its own definitions for some types, e.g. bullet lines rather than list items); the measured share is then limited by the constraints the potentials do not enforce (keywords, forbidden words, case, JSON, starts-with, one-of, title, postscript, frequencies) and by what the compiler reads from the prompt (it is conservative: a request it does not understand is neither enforced nor checked by our verifier; the harness's checker still scores it).
- The costs: tokens and decoder steps per turn, and the fluency proxy, i.e. how far the potentials pull the chosen reply away from what the model itself finds likely.

What it cannot show:

- **How our model responds to the potentials.** The gain of masking and reweighting depends on how much probability the model already puts on compliant continuations. Falcon-H1-Tiny is a post-trained instruct model that already follows many explicit constraints; our 20M-active model will have seen hindsight constraints and the countdown registers in training (PLAN 5 item 8), which changes both the baseline rate and how often a mask has to bind. The size of the gain here is not a prediction for our model.
- **Judge preference.** No judge runs here: whether the length band and the consensus make replies better for a reader (PLAN 5 item 6) is for the blind A/B harness; the stand-in only shows what they do to the exact measures above.
- **Coherence in the literature's sense.** The model's own mean log-probability per token is a weak proxy (repetitive text scores well); it is reported together with the degenerate and cut-off rates, not instead of a coherence rating.
- **Parts that only exist for our model**: the calculator spans (forced results), the candidate tape, the library passage and the copy-cap exemptions, n-gram blocking (off in every arm here), the critic (the gate's rho >= 0.3 condition for using it cannot be measured without a critic), and the twist.
- **Speed on the target hardware.** The numbers are one CPU thread per process on a machine shared with other work; our model on the TPU decodes all particles in one batched step, so the relative cost of six particles is far smaller there.
- **Statistical power.** With this many prompts the 95% intervals are wide; differences smaller than about 15-20 percentage points in a share are not resolved, and the paired sign tests are the sharper comparison.
- **Unseen prompts.** The constraint figures are in-sample for the constraint compiler (Setup): on the held-out half it reads every annotated constraint of 85% of the constrained prompts against 96% here, so the gains of the filter and the potentials on new prompts (the held-out claim, the arena) will be smaller. A future gate should keep part of the dev prompts out of compiler development and measure on that part.

## Gate E9 (PLAN section 7)

The gate asks for a significant rise of the constraint satisfaction rate without a drop in coherence, and a within-prompt rank correlation rho >= 0.3 before the critic is used; otherwise K = 1 or filtering only.

- **On the stand-in the first condition holds**: 66% -> 98% of the constrained prompts (15 better, 0 worse, p = 0.0001), no degenerate replies other than those that ran out of budget (9 of 63 with the potentials, against 7 with the filter and 11 with plain sampling), and the fluency proxy moves by -0.025 ± 0.019 nats per token (not significant). The filter alone already gives 91% (12 better, 0 worse, p = 0.0005); the extra gain of the potentials over the filter is 3 prompts to 0, which this sample does not resolve, though it is certain by construction for the counts the potentials enforce. These are dev prompts on which the constraint compiler was developed (Setup); on unseen prompts the gain will be smaller.
- **The critic condition cannot be measured** here (no critic): the critic stays off.
- **Decision for our model**: keep K = 6 with potentials, filter and consensus as the decoder's default, and re-run these three arms on our checkpoint before freezing it (the harness drives our generator with the same switches: `particles`, `potentials`, `band` in the arm's settings; `bes.decode.respond`). Fall back to "filter only" (`potentials: false`) if the paired fluency difference on our model is significantly negative, and to K = 1 if the filter does not raise satisfaction there.
- **Two things to fix or watch before that run**: (1) budget forcing: with a budget smaller than what the model wants to write, budget-aware potentials turn "unfinished" into "ended at the budget" (14% here); the selector's new `at_budget` check prefers a particle that ended on its own, but when every particle runs long the reply is still cut, so the budget for open prompts should exceed the length the model was trained to produce (PLAN: 80-200 words), or the length band should steer the particles (a twist), not only filter them; (2) forbidden words, letter case and other token-local constraints are only filtered, not enforced (`constraints.token_local` describes how each could be masked).

## Implementation notes found while measuring

- **Copying particle states in llama.cpp.** `llama_memory_seq_cp` on this hybrid attention + SSM model shares the recurrent cell lazily; after copies in the middle of decoding, the sequences involved gave log-probabilities that differed from a fresh evaluation of the same tokens by up to 0.8, while the sequences not involved matched exactly, so resampling would silently corrupt particles. `GGUFLM.reorder` copies whole sequence states with `llama_state_seq_get_data` / `llama_state_seq_set_data` instead (about 5.5 MB per copy here, about 4 ms); the tests compare every particle after steps, inactive steps and two resamplings with llama-cpp-python's high-level `Llama` fed the same way (agreement within 1e-6).
- **Two numerical properties of llama.cpp on this model.** (1) The result depends on the batch shape: the same tokens evaluated as one batch and one at a time differ by up to about 2 in a tail log-probability (the decoder always feeds the prompt as one batch, then one token per step, and its log-probabilities are those of that path). (2) It depends on the attention kernel: the context default (flash attention) and the plain kernel that `llama_cpp.Llama` uses by default, as in the harness's `bes/eval/proxy/run_gguf.py`, differ by a total variation of about 0.003 per next-token distribution. This run used the context default for every arm, so the arms are comparable with each other; the plain arm is therefore a slightly different numerical version of the opponent than the harness's. `GGUFLM(flash_attn=False)` reproduces the harness's kernel (tested).
- **Vocabulary.** 332 control tokens become special tokens (never sampled under the structural potentials), `<|im_end|>` is `END`, `<|begin_of_text|>` is `BOS`, three virtual ids carry the calculator kinds (the model gives them probability 0), and the 3 tokens longer than 127 bytes are special for the exact layer (its tables store byte counts in int8) but keep their bytes in the visible text. The transducer tables for the 32,771 ids build in about 2 s; a count specification compiles in about 0.6 s.
- **Throughput** (one thread, the machine shared with other work): llama.cpp evaluates about 55-95 tokens/s for one sequence and about 130 tokens/s for six sequences in one batch; through the decoder about 37 tokens/s (K = 1) and about 60 tokens/s summed over six particles on a quiet machine, and 27 and 43 tokens/s during this run (each worker had about half a core). About a third of the decoder's step time is `sampling.truncation_keep`, which sorts the whole 32k vocabulary twice per row (top-k, then top-p); a partial sort with the same tie rule would give the same keep sets.
