# E1 — library coverage (written library, Simple English Wikipedia)

Generated by `scripts/measure_coverage.py` (stages `tune`, `pool`, `lib`, `readset`, `report`). All numbers below are measured; nothing is extrapolated. Recall@k = share of questions for which one of the normalised answer strings occurs as a whole-token sequence in one of the top-k passages (title line + body). This is a proxy: a passage can contain the answer string by chance, and can answer a question without containing the exact string.

Question samples: NQ-open validation 3608 (all with answers), TriviaQA rc.nocontext validation 3000 (seeded sample), PopQA 3000 (seeded sample), Dolly-15k 1200 instructions (150 per category). Dev sets used for every choice (BM25 weights, gate thresholds): NQ-open train sample 1999, TriviaQA validation sample 2000 disjoint from the evaluation sample.

## Candidate pool and cleaning

- Source: `wikimedia/wikipedia` 20231101.simple (241,787 articles, 267.5M characters).
- Kept 235,252 articles, 542,954 passages, 189,172,330 bytes of passage text; dropped: disambiguation 3,110, empty 1,892, list_only 825, list_page 708.
- Rule effects over the whole dump: tail sections cut in 177,548 articles (760,142 lines); a final category group found and removed in 228,069 articles; 545,807 table-row/image lines and 202,447 list items of fewer than 3 words dropped; 7,626 sentences ending in a dangling word (removed template) dropped; 2,374,072 list words removed from list-heavy pages (date, year and month pages).
- Exact duplicate passage bodies: 1,115 (never selected).
- The whole pool packs into **34,899,906 stored numbers** (text blocks + directory + titles), so every budget of 35M numbers or more holds all of Simple English Wikipedia.

## What the library cannot answer

- NQ-open (real search-engine questions, the closest of these sets to everyday questions): with exact BM25 over all of Simple English Wikipedia, **73.5%** have no answer string in the top 3 passages, 58.3% none in the top 20, 47.6% none in the top 100; for **17.5%** (sample of 200) no answer string occurs anywhere in the library text.
- TriviaQA: 48.8% no answer in the top 3, 23.8% none in the top 100, 5.0% (sample of 200) answer absent from the whole library.
- PopQA: 80.6% no answer in the top 3, 60.1% none in the top 100.
- Everyday prompts that are not factual look-ups (Dolly brainstorming, classification, creative_writing, information_extraction, summarization): the gate returns a passage for brainstorming 4.7%, classification 10.7%, creative_writing 7.3%, information_extraction 8.7%, summarization 12.0%.

## Notes

- Codec (measured on a 1/6 sample of the dump: 40,187 articles, 93,007 passages, 64 kB blocks): raw LZMA2 preset 6 compresses 2.778x at 3.9 MB/s per thread, preset 9 and 9e give the same ratio at 1.4 MB/s; pb=0 adds 0.3% (2.785x); ordering articles by first category then title adds 1.2% over dump order (2.813x vs 2.779x on all 495 sample blocks). Chosen: preset 6, lc=3, lp=0, pb=0, dict 64 KiB, category order.
- Fixed-width index rows do not work: with 2^18 buckets x K=7 postings (3,932,177 numbers) only 643,459 of the 1,835,008 slots were filled on the 20M library (most buckets hold one to three rare-term postings), while every moderately common term was cut to 7 passages; recall fell to NQ 5.6/9.6, TriviaQA 14.1/21.5, PopQA 7.4/12.2 (R@1/R@3) against 16.8/24.3, 35.5/47.3, 12.8/18.5 for the untruncated hashed index (first pool version, before the last cleaning fixes; 299,505 passages).
- Posting selection, compared on dev questions only (20M library, 1.8M postings, dev NQ / dev TQA R@1 and R@3): term-centric top-7 per bucket 4.4/7.2 and 14.3/22.8; document-centric top-6 per passage 6.5/10.3 and 20.7/29.5; relative impact x passage prior 10.4/16.3 and 26.5/37.4; with relative impact^0.5 10.7/16.3 and 28.0/37.6; with prior^1.5 10.5/16.3 and 28.2/37.8; with a 2x title-term bonus 10.8/16.7 and 27.6/37.6; untruncated 13.2/21.5 and 36.4/47.1. The shipped rule combines the three refinements (rel^0.5 x prior^1.5 x title bonus 2); its own numbers are the default rows of the tables above.
- Hashing alone is cheap: on every library the untruncated 2^18-bucket index (8-bit impacts) is within 1 R@1 point (0.2-0.9) of exact BM25 over true terms; nearly all of the loss comes from truncation to the storage budget.
- BM25 weights: the tuning grid (k1, b, title weight, lead-title weight; 54 settings) ran on dev questions only; the chosen setting (0.6, 0.3, 1, 6) beats the classic (0.9, 0.4, 1, 1) by less than one R@1 point, inside the sampling error of 2,000-question dev sets (about +-1 point).
- Budget: all of Simple English Wikipedia packs into 34.9M numbers (text 32.9M, directory 1.0M, titles 1.0M), so the 40M and 60M libraries are identical (the whole pool) and the plan's 60M+4M allocation leaves about 25M numbers unused. On the whole pool a 16M-number index raises R@1 from 12.0 to 14.9 (NQ) and from 28.9 to 35.5 (TriviaQA) over the 4M index; beyond about 16M the 1024-posting list cap binds (7.7M postings at 16M, 8.0M at 32M), so a larger index also needs a larger cap (more numbers read per query). Spending the spare numbers on the index is the measured option; English Wikipedia lead paragraphs (plan section 4D) were not measured.
- Token counts use the proxy len(utf8)/3.3 bytes per token (the BPE tokenizer did not exist yet), which caps passages at about 528 bytes (about 85 words including the title line) instead of 110 words; rebuild the pool with the real tokenizer's count_tokens before training, which will give somewhat longer passages and slightly higher recall@1.
- Read set against the plan's ledger (about 450 numbers for the index): the variable-length lists make the index part of a query larger - mean 4.1k numbers on NQ, largest observed 29.8k, bounded by about 34k (16 lists x 1024 postings x 2 numbers + counts, coarse offsets and df). A text block averages about 11.4k numbers (worst case 32,776 for an incompressible 64 kB block). The largest whole retrieval observed read 42.2k numbers, inside the ledger's 32k-64k per-retrieval envelope.
- Gate: with only Simple English Wikipedia the single returned passage contains an answer string for at most about 40-45% of the questions it is returned for at useful coverage (dev frontier); the default gate therefore uses a dev precision floor of 0.35 (`--precision-target`) instead of 0.5, which would leave a few percent coverage. The query-coverage feature only helps at the strict end of the frontier and is off by default. The threshold should be revisited with E3 (reading ability with BM25 passages and robustness to irrelevant ones).
