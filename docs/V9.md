# v9: token pages on a dense looped core

`configs/v9.py` is an alternative to `configs/final.py`. It keeps the dense looped core, drops
the written library and spends the stored numbers this frees on one *page* per vocabulary id:
private feed-forward neurons, a gain on the attention output, and the value embedding the
model already had. Every new part is behind a configuration flag and a run-time switch; with
the flags at their defaults the existing configurations are unchanged. Three further parts are
implemented and left off because the evidence does not carry them: a head-wise gate on the
attention output, selective attention, and gains on values and feed-forward neurons (sections
8 and 9).

Nothing here has run on a TPU. The evidence is a small CPU lab (one seed per arm), the
literature, compile-only checks for v6e and the test-suite. Section 8 lists what that does and
does not support.

## 1. The question

The budget is 100M stored numbers, at most 20M read per generated token, and one 24-hour run on
one TPU v6e. The dense looped core already reads about 19M. What should the other 80M be?
The first design used them for a written library with retrieval; a second proposal (never
implemented) was token-routed feed-forward experts, which need a dispatch kernel on TPU. v9
answers with measurements of *where* token-keyed parameters help and *in which form*, and
needs no dispatch: every page is a row of a lookup table.

## 2. Measurements

Three regularities:

1. **Read / write asymmetry.** Token-specific parameters on the matching side of attention
   (queries, keys) hurt; on the writing side (values, outputs) they help, and the two effects
   add (-0.115 + 0.056 = -0.059, measured -0.042 for all four). The same order is published
   for learned-router attention experts (SwitchHead: values/outputs 12.27, dense 12.31, all
   four 12.57, queries/keys 12.90 perplexity) and for token memories (Memory Attention: values
   best, queries and keys below the baseline). Class-specific queries alone or keys alone
   cost little (+0.016, +0.004); both together cost three times their sum: matching needs
   queries and keys of every pair of classes to live in one coordinate system, and one shared
   side provides it. Writing needs no such agreement.
2. **Multiply where the stream is pure context.** A per-token gain on the attention output is
   worth -0.07 to -0.09; per-token gains on FFN neurons, whose input already contains the
   token and whose ReLU^2 already multiplies, are worth -0.03 with four times the storage.
3. **One law for feed-forward neurons.** Dense widening, class experts and private neurons
   (uniform, by frequency, capped) all fit

       dL = -c * E_{x ~ f} [ ln( n(x) / n0 ) ]

   where `n(x)` is the number of neurons per token type available to token `x` (shared
   neurons count `width / V`, a class expert `width / tokens in the class`, private neurons
   fully) and `n0` the base value. One constant fits ten arms at 6.6M tokens (c = 0.070, rms
   residual 0.008 nats, largest 0.019) and eight at 12M (c = 0.078, rms residual 0.015). A
   neuron in the shared low-dimensional space counts as about 0.37 of a full-width one at a
   quarter of its storage.

The complete page is robust to the learning rate of the neuron values on the high side (three
times higher: -0.213 at 12M against -0.212) and loses on the low side (three times lower:
-0.185). A value gain on top of the page adds -0.015.

## 3. Mathematics

**Water-filling.** If token `x` gains `c ln(1 + rho_x / n0)` per position from `rho_x` owned
neurons, the allocation maximising `sum_x f_x c ln(1 + rho_x / n0)` under `sum_x rho_x = R`
is `rho_x = max(0, f_x (R + |A| n0) / F_A - n0)`, with `A` the tokens that receive anything and
`F_A` their total frequency: proportional to frequency above a threshold. Fitted on two arms
(uniform; by frequency with cap 32) the model predicts the third (cap 8) as -0.218 against
-0.221 measured. The same condition says when a finer key (a token together with its left
context) deserves a page of its own: when its frequency times its value per position exceeds
the water level. The published law for hashed n-gram input tables (loss falls by 0.0256 per
decade of rows at 1.3B; a table of 1e5 rows is worth about 0.007 nats) puts such keys below
the level at this budget, so v9 has no n-gram table.

**Dimension.** The token-neuron family
`f(x, h) = P_out^T sum_j relu(<k_{x,j}, P_in^T h>)^2 v_{x,j}` has generic dimension
`V rho (2 dk - 1) + 2 d dk - 2 dk^2` (one scaling per neuron, one GL(dk) on each side;
checked numerically by the rank of the Jacobian on small instances). For the final shape that
is 25.3M per block, of which a token reads 3,072 private numbers and 0.29M shared ones. Any
parameterisation that reads all its numbers for every token and contains this family reads at
least 25.3M per block.

**Exact reduction.** New tables start at zero where they are added to or multiplied into the
stream, and every mechanism has a switch, so the v9 parameter tree with untrained pages
computes the function of the same model without them, bit for bit (tested), and each
mechanism can be turned off without recompiling.

**Scatter-free table gradients (`table_grad = "sorted"`).** For `m` looked-up rows of width
`W` from a table of `R` rows: sort the row ids; cut the sorted rows into chunks of `C`; in
each chunk multiply by the one-hot matrix of the *rank of the run of equal ids* (`C x C`
instead of `C x R`); assemble the gradient of a table row from at most three pieces (the last
run of its first chunk, all whole chunks in between through prefix sums of the chunk totals,
the first run of its last chunk). The cost is `2 m C W` multiply-adds instead of `2 m R W`:
16 times less for `C = 512`, `R = 8192`. Sort, gathers, compares, matmuls and cumulative sums
only.

## 4. Architecture

```
token page (per vocabulary id)                              numbers per token
  input embedding                 emb/tok                      768              (existing)
  per-loop value embedding        emb/ve                       8 x 128          (existing)
  attention output gain           gain/o                       2 blocks x 768
  token neurons                   page/key, page/val           2 blocks x 8 x (192 + 192)

dense, shared by all tokens
  looped core, lanes, head                                     as in the final configuration
  token-neuron projections        page/pin, page/pout          2 blocks x 2 x 768 x 192
```

In loop `r` and block `i`, at a position holding token `x`:

```
attention:  y = kernel(q, k, v)                                  # queries and keys shared
            a = (y * (1 + gain * g_o[x, i])) @ W_o
feed-forward:
            z   = rmsnorm(x_ffn @ P_in[i])
            a_j = <rmsnorm(key[x, i, j]), z> / sqrt(192)          # j = 1..8
            u  += mlp(x_ffn) + page * (sum_j relu(a_j)^2 val[x, i, j]) @ P_out[i]
```

Also implemented and off in `configs/v9.py`: a head-wise gate on the attention output
(`attn_gate`: `y_h <- y_h * (1 + gate * (2 sigmoid(x_in @ w_h / d + b[r, h]) - 1))` before the
gain, 9,312 numbers in `core/attn/gate_w`, `gate_b`), gains on the values (`gain_v`) and on FFN
neurons (`gain_ffn`), separate gain rows per group of loops (`gain_phases`), and selective
attention (`sel_attn`; dense attention path only).

## 6. Cost

* Compute. Per block application the token neurons add two projections of width 192
  (`2 * 2 * 768 * 192` multiply-adds forward, 4.2% of the block's matmul work) and two
  contractions over 8 neurons; the gains are elementwise products. Nothing is dispatched,
  sorted or dropped in the forward pass.
* Device memory traffic. The page rows of a micro-batch are gathered once (`[B, T, 8, 192]`
  keys and values per block in the activation dtype, about 0.2 GiB per block at 32 x 1024) and
  read in every loop; their cotangents accumulate over the loops in the same dtype. This, not
  the arithmetic, is the cost of the mechanism; it has not been measured on a TPU.
* Table gradients. The five token-indexed tables have a total row width of 9,472. Their
  one-hot gradient costs `2 n V W` multiply-adds, about a fifth of the matmul work of a
  training step; the `"sorted"` mode brings that to about 1.5%. The start-up benchmark times
  the modes within its time budget and keeps the fastest it measured; on a host that compiles
  as slowly as this container the budget ends before the other modes (`RUNBOOK.md` section 1.4).

## 7. What to expect

The calibrated scaling law of this project puts the final configuration at 2.507 nats per
token and Falcon-H1-Tiny-90M at 2.358. For v9:

* Published gains of token-keyed tables at two to four times the dense storage, at 45M to
  1.5B dense parameters, are 0.04 to 0.11 nats (or one to two points of benchmark average).
  With that range, minus the time cost, v9 lands at about 2.45 (2.41 to 2.48).
* If the lab's law held at full scale (private neurons counted like dense ones with the
  measured factor 0.37), the same arithmetic gives about 2.27 to 2.29. The lab is in a regime
  where this kind of storage is worth most, so this is an upper end, not an expectation.

v9 therefore narrows the predicted gap to the 90M opponent and does not close it on
validation loss alone; the blind comparison still depends on the chat mixture, preference
optimisation and decoding of the plan, which v9 does not change.

## 8. Limits of the evidence

* The lab is tiny, and count-based n-gram models beat every neural arm at its data size:
  token-keyed storage is worth more there than at full scale.
* One seed per arm; the paired noise of the lab is about 0.01 nats.
* The micro ablations of this repository (d = 128, 1M tokens in 244 steps, 8,192 token types)
  give a page row about a hundred visits: they can show harm, hardly benefit. Relative held-out
  loss against the reference with the same seed and data order (share-weighted web and chat;
  `scripts/micro_ablate.py`, arms of kind `add_new`; records and the script of this table in
  `lab/v9/micro/`):

  | arm | 250K | 500K | 1M tokens | web / chat / assistant at 1M |
  |---|---|---|---|---|
  | output gains (`gain_o`) | -0.06% | -0.15% | -0.29% | -0.25 / -0.44 / -0.45 |
  | token neurons (`tok_neurons`) | -0.13% | -0.08% | -0.32% | -0.28 / -0.46 / -0.37 |
  | both, the page of `configs/v9.py` (`v9_pages`) | -0.22% | -0.32% | -0.61% | -0.54 / -0.83 / -0.72 |
  | the page with a decay of 0.1 on both tables (`v9_pages_decay`) | -0.22% | -0.32% | -0.62% | -0.56 / -0.83 / -0.72 |
  | gate (`attn_gate`) | +0.04% | +0.01% | -0.02% | -0.02 / -0.02 / -0.04 |
  | the page and the gate (`v9_pages_gate`) | -0.19% | -0.26% | -0.57% | -0.52 / -0.73 / -0.61 |
  | first version of the gate (logit `x @ w`, not in the repository) | +0.19% | +0.54% | +0.80% | +0.69 / +1.22 / +1.25 |
  | the page and that gate | +0.11% | +0.61% | +0.79% | +0.75 / +0.91 / +1.01 |

  The sampling error of these paired differences is 0.01% to 0.08%. The seed replicate of the
  E2 report (another data order and initialisation) differs from the reference by 0.42%, which
  puts the margin of the pre-registered rule at 0.84%, and that rule asks 1% of a new component.
  By the rule the page is not resolved. What the run does show: the two page paths have the same
  sign in every domain, grow with the tokens and add up (-0.29% and -0.32% alone, -0.61%
  together), and nothing is harmed. The evidence for the size of the gain is the lab, not this
  run. `sel_attn` and `v9_pages_lr03` are defined and were not run. The arms train with the
  scatter-add table gradient (`take`, the fast mode on a CPU); that `sorted` trains the same to
  float32 round-off is checked by a test (`tests/model/test_model_train_v9.py`), not by an arm.
* The gate. Its first version computed the logit as `x @ w_h + b`. `w_h` has `d` entries and
  Adam moves each by about the learning rate per step, so the logit moved `d` times faster than
  a scalar of the same group. After 244 steps the trained weights gave logits of standard
  deviation 1.3 to 2.0 on unit-RMS inputs, 9% to 26% of the gate values were below 0.2 or above
  1.8, and the loss was 0.8% higher (1.2% on chat). The function and its gradient were right, so
  no test and no reviewer saw it; the ablation did. With the logit divided by `d` the
  position-dependent part stays small over a run of this length (standard deviation 0.03 to
  0.06), the per-loop biases reach +-0.5, and the effect on the loss is nil. A part without an
  effect and without a measurement of its own behind it is not shipped: `attn_gate` is off.
* Decay. The page groups can train with a decoupled decay (`page_decay`, `gain_decay`); it is
  0 in `configs/v9.py`. An earlier draft used 0.1, on the argument that it keeps rows whose
  gradient is noise near zero. Under Adam a decayed coordinate settles where its normalised
  step equals `decay * |value|`. For a coordinate that gets `n` visits per step, each with
  gradient noise `s` and curvature `h`, the normalised step at distance `delta` from the
  optimum is about `sqrt(n) * h * delta / s` while the noise dominates, so the coordinate
  settles a fraction `decay * s / (sqrt(n) * h)` short of its optimum. `s / h` is the distance
  at which one visit's mean gradient equals its noise, and it can be many times the value
  itself: with 0.1 the shortfall is small for the most frequent tokens and can be most of the
  value for tokens seen a few tens of times per step, once the 80,000 steps of the real run
  have reached that equilibrium. 244 steps cannot show it (the two arms above are equal); the
  lab's 1,500 steps ran with a decay too weak to act (0.01 at a rate of 5e-3: at most 7% over
  the run); and the other per-token tables of this model, the input and the per-loop value
  embeddings, train under Adam without decay. So: none.
* The learning rates of the page groups (`lr_page`, `lr_gain`) come from the lab (the neuron
  values lost with a rate three times lower and were unchanged with one three times higher) and
  from the conventions of the existing Adam groups; they have not been tuned at scale.
* Nothing has been timed on a TPU. The start-up benchmark and the canary of the supervisor are
  the first measurement; the ladder switches the new mechanisms off first.

## 9. Not adopted, with the reason

| candidate | reason |
|---|---|
| token-specific queries or keys | hurt in the lab (+0.046) and in two published studies |
| gains on FFN neurons | -0.035 in the lab at four times the storage of the output gain; implemented, off |
| token-routed FFN experts with a dispatch kernel | matched by private neurons at equal storage in the lab (-0.183 against -0.184 to -0.242) without dispatch, capacity factors or dropped tokens |
| neurons allocated by frequency | better at equal storage (-0.242 against -0.170), but storage is not the binding constraint: the uniform allocation at the cap contains it |
| hashed n-gram input tables | published slope 0.0256 nats per decade of rows; about 0.007 nats for a table that fits here |
| selective attention as the default | -0.022 with rotary positions at 110M (one seed), needs the dense attention path; implemented, off, with a throughput rule in the benchmark |
| head-wise gate on the attention output | published evidence conflicts (-0.050 in a looped 1.3B model without QK-norm; no gain in a 1.2B study once QK-norm is present) and the lab has no arm for it; in the micro ablation it is neutral (-0.02% at 1M tokens) with the logit scaled by `1/d` and harmful without that scale (section 8); implemented, off |
| short causal convolutions, forget-gate bias, exclusive self-attention | expected 0.002 to 0.02 each with overlapping mechanisms; not implemented |

## 10. What was verified

Compile-only for v6e (`bes.train.aot`, bfloat16, 8 micro-batches per step, rematerialisation
on, flash attention kernel; the limit is 28 GiB of device memory):

| program | shape | table gradient | compile s | peak GiB | scatter / gather / Mosaic kernels |
|---|---|---|---|---|---|
| train step | 32 x 1024 | sorted | 375 | 7.01 | 0 / 57 / 8 |
| train step | 32 x 1024 | onehot | 353 | 7.17 | 0 / 9 / 8 |
| train step | 16 x 2048 | sorted | 348 | 7.01 | 0 / 57 / 8 |
| train step | 16 x 2048 | onehot | 322 | 7.17 | 0 / 9 / 8 |
| decode step | 8 rows, 2048 cache slots | | 9 | 1.89 | 0 / 9 / 0 |
| prefill | chunk 256, 2048 cache slots | | 16 | 0.58 | 0 / 8 / 0 |

(the train step of `configs/final.py` peaks at 4.21 GiB). Compile times are from one shared
CPU core and say nothing about the TPU.

Tests: exact reduction to the model without the flags (zero pages, each switch at 0); an
independent numpy reference of every new path; float64 gradient checks of every new leaf; the
`"sorted"` gradient against a scatter-add on adversarial inputs; generation with the key-value
cache against the full forward for all new paths (chunkings, ragged batches, particles); the
read-set reference, poisoning and gradient-support audits with the new tables; budget, roles
and optimiser groups; the benchmark's plan search with the three table modes; the supervisor's
ladder. A CPU rehearsal of the whole 24-hour pipeline at smoke size with the flags of
`configs/v9.py` completes: benchmark (plan `xla-remat1-ms16-sorted`), canary (deterministic,
safe and full switches pass), 214 training steps, sampling, critic, preference optimisation,
decode selection, the judged comparison and the export with its held-out check. An earlier
rehearsal, with the gate also on, was killed in the middle of training and resumed to the end.

The read-set logger measures 19.43M numbers at the worst position of `configs/v9.py` without
the critic and 19.63M with it; the strict reading on 40 real documents (ClimbMix samples of at
least 2,048 tokens, real exact-layer features) is 21.2M to 24.6M at 1,024 positions (median
23.8M) and 22.4M to 28.2M at 2,048 (median 26.7M).
